High

내부 예외 메시지가 HTTP 응답에 그대로 포함됨. 공격자가 획득 가능한 정보: 내부 파일 경로, 서버 설정 구조, 향후 DB 오류 메시지.

except Exception as e:

예외 추상화 처리. 서버 로그에만 기록하고 클라이언트에는 일반 메시지 반환.
H-02   영구 마스터키(appkey/appsecret)가 모든 요청에 노출 — 서버 설계 구조 취약점
High
실증: Bearer 토큰 없이 appkey/appsecret만으로는 호출 불가이나, appkey/appsecret 없이 Bearer 토큰만으로도 호출 불가 — 서버가 두 가지를 동시에 필수로 요구.

표준 OAuth 2.0에서 client_secret(appsecret)은 토큰 발급 시에만 사용하는 마스터키. 이후 API 호출엔 노출하지 않는 것이 원칙.

KIS 구조의 문제:
인증 수단만료노출 빈도탈취 시 피해
Bearer 토큰24시간매 요청최대 24시간
appkey/appsecret영구매 요청재발급 전까지 무기한
토큰 발급의 실질적 의미 상실: appkey/appsecret을 탈취한 공격자는 토큰을 무효화해도 즉시 새 토큰을 재발급할 수 있음. 즉 Bearer 토큰은 보안 레이어가 아닌 API 관리 레이어(rate limit, 감사 로그)에 불과.
서버 설계 수준의 개선 필요. API 호출 시 appkey/appsecret 불필요하도록 인증 구조 재설계 검토. 단기 완화: appkey/appsecret 노출 최소화 (저장 암호화, 전송 경로 제한, 탈취 시 즉시 재발급 프로세스 정립).
🟡 Medium
M-01   hashkey 비활성화 — 종심 방어 미적용
Medium
주문 변조 방지용 hashkey 호출이 주석 처리됨. TLS로 네트워크 MITM은 방어되지만 Replay Attack 및 로컬 악성코드의 파라미터 조작은 방어 불가. 
# 현재 — 주석 처리
# if (hashFlag): set_order_hash_key(headers, params)
종심 방어 관점에서 주석 해제 권장.
M-03   Rate Limiting 없음
Medium
실측: 10회 연속 무제한 허용 확인.
POST /login, POST /switch-mode 엔드포인트에 요청 횟수 제한 없음. AI 자동화 공격 시 credential stuffing 및 서비스 불안정화 가능. (2026년 금융권 해킹 동일 패턴)
slowapi 등 rate limiting 적용. switch-mode 쿨다운은 Redis 기반으로 변경.
M-04   WebSocket 구독 제한 클라이언트 사이드만
Medium
40개 구독 제한이 클라이언트에만 존재. 서버 사이드 강제 여부 미확인. 우회 시 서버 부하 유발 가능.
서버 사이드 구독 수 제한 적용 여부 확인 필요.
🟢 Low
L-01   액세스 토큰 평문 파일 저장
Low
토큰이 ~/KIS/config/KIS{날짜}에 평문 저장. 유효기간 24시간. 로컬 악성 프로세스 또는 타 사용자가 파일 접근 시 탈취 가능.
파일 권한 chmod 600 적용, OS keychain 활용 검토.
